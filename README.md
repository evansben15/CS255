DriverPass Project Summary
The client for this project was DriverPass, a company founded to address a gap in driver education. Their research found that more than 65% of students fail their DMV driving tests because they only study previous tests without adequate hands-on practice. They wanted a web-based system that would allow students to access online practice exams, track their test progress, and schedule on-the-road driving lessons with certified instructors. The system also needed to support multiple user roles including customers, a secretary, an owner, and an IT officer, each with different levels of access and functionality.
What I Did Particularly Well
I think I did particularly well on the requirements gathering and documentation phase. The business requirements document captures the client's needs in a thorough and organized way, covering functional requirements, nonfunctional requirements, security considerations, and system limitations. I was careful to tie each requirement back to something specific the client mentioned in the interview transcript rather than making assumptions, which helped keep the document grounded in what DriverPass actually needed rather than what I thought they might need.
What I Would Revise
If I could revise one part of my work, I would improve the UML class diagram. While it captures all the major classes and their attributes, I would add methods to each class to show not just what data each object holds but what it can do. For example, the Reservation class would benefit from methods like create(), modify(), and cancel() to make the design more useful as a blueprint for developers. Adding methods would make the class diagram a stronger bridge between the design document and actual implementation.
Interpreting User Needs
I interpreted the user's needs primarily by carefully reading the interview transcript and identifying both explicit requests and implied requirements. For example, the client explicitly asked for appointment scheduling and online practice tests, but the need for role-based access control was implied by the fact that different users needed different capabilities. I implemented these needs into the design by mapping each requirement to specific use cases, classes, and system behaviors in the UML diagrams. Considering user needs is critical in system design because a technically correct system that doesn't match what users actually need will fail in practice, the goal of any system is to solve a real problem for real people, and losing sight of that leads to wasted development effort and a product no one wants to use.
Approach to Designing Software
My approach to designing software starts with thorough requirements gathering before any technical decisions are made. Understanding what the system needs to do, and who it needs to serve, is the foundation everything else builds on. From there, I use a blended modeling approach: process models like activity and sequence diagrams to capture how the system behaves over time, and object models like class and use case diagrams to capture the structure of the system. In the future I would continue using this blended approach and would also prioritize early stakeholder feedback on diagrams before moving into detailed design, since it is much easier to catch misunderstandings at the diagram stage than after development has begun.
